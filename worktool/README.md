# 生活工具箱 · v1.13.3

泛生活人群的多功能在线工具箱工作台。**多文件交付、零外部依赖**：样式与脚本都是本目录下的独立文件（CSS 9 个、JS 18 个，按层拆分；另有自托管的 libwebp WASM 编码器），45 个界面图标为内联 SVG sprite（见「图标系统」一节），不引用任何 CDN、字体服务或组件库。

当前状态：**四个可用的工具** —— 图片格式转换、GITHUB 链接转换、单位换算、日期天数计算。侧拉栏分 4 组共 10 项（其中 6 项为已排期的占位）；**首页只列已上线的工具**。

## 一、快速开始

### 方式 A：本地起一个静态服务（推荐）

多文件项目应当通过 HTTP 访问，这也是手机端唯一可行的方式。任选一条：

```bash
cd 生活工具箱-v1.13
python3 -m http.server 8787        # 然后浏览器打开 http://localhost:8787
```

macOS 上也可以直接双击 `启动本地服务器.command`（首次使用需 `chmod +x 启动本地服务器.command`），它会自动起服务并打开浏览器。

> **现在也能直接双击 `index.html`。** v1.5.0 把图标换成内联 sprite 后，`file://` 下与 HTTP 完全一致，不再有任何降级路径（此前用 CSS `mask` 引用独立 SVG 会被 CORS 拦截）。唯一差别是 `file://` 下 Service Worker 不注册，因此没有离线缓存，功能不受影响。

### 方式 B：部署到静态托管

整个目录原样上传即可（GitHub Pages / Vercel / Netlify / 任意对象存储静态站）。没有构建步骤，没有后端，没有环境变量。

#### GitHub Pages 特别注意

**可以，且不需要改一行代码** —— 已按「项目站」（`https://<用户名>.github.io/<仓库名>/` 这种子路径形式）实测通过。下面三条照做就行：

1. **把本目录的内容放到仓库根目录**，不要连 `生活工具箱-v1.13/` 这层文件夹一起提交。
   否则访问地址会变成 `…github.io/<仓库名>/生活工具箱-v1.13/` —— 能用，但中文路径会被百分号编码成一长串。
2. **保留根目录的 `.nojekyll`**（本包已带一个空文件）。
   GitHub Pages 默认会跑一遍 Jekyll 构建，`.nojekyll` 用来关掉它，避免构建环节引入意外。
3. **仓库 Settings → Pages → Source 选 `Deploy from a branch`，分支 `main`、目录 `/ (root)`**，保存后等一两分钟。

为什么它天然适配：

| 特性 | 为什么在 Pages 子路径下没问题 |
|---|---|
| 路由 | 用 **hash 路由**（`#/imageconvert`），不依赖服务端重写，不需要 `404.html` 兜底 |
| 路径 | 全部是**相对路径**，没有一处 `/assets/...` 这种绝对路径 |
| Service Worker | `register('sw.js')` 是相对注册，作用域自动落在 `/仓库名/` |
| Manifest | `start_url` 与 `scope` 都写的 `./`，安装到主屏后不会跳错目录 |
| 文件名 | 资源文件名全是 ASCII，不涉及大小写不匹配（Pages 是 Linux，大小写敏感） |

> 自定义域名（`CNAME`）或用户站（`https://<用户名>.github.io/` 根路径）同样可用，这两种情况下路径更简单，不会有任何差别。
>
> `启动本地服务器.command` 是给你本地开发用的，传到 Pages 上不影响运行，只是会被当成一个可下载文件。

### 图片格式转换

| 能力 | 说明 |
|---|---|
| 输入方式 | 拖拽、点击选择、`Ctrl / ⌘ + V` 粘贴剪贴板图片，支持多选与格式混合 |
| **输出格式自选** | WebP / JPEG / PNG 三选一，选择会存下来 |
| **两条编码路径** | WebP 走自带 libwebp 的 WASM 编码器（参数可控、支持无损、全平台可用）；JPEG / PNG 走浏览器原生 Canvas |
| 转换参数 | 输出质量 40–100%（**100% 即无损**）、最长边限制、文件名后缀 |
| 批量处理 | 串行队列，逐张显示进度，单张失败不阻塞其余；可重试、可移除 |
| 结果呈现 | 原体积 → 输出体积、缩减百分比、尺寸变化、体积对比条，并标注「无损」或「质量 x%」 |
| 智能提示 | 识别出颜色少的图（截图 / UI / 图表）且有损编码时，提示可改无损 |
| 下载 | 单张下载、一键下载全部（自动错开间隔，避免浏览器拦截） |
| 历史 | 记录文件名与体积（不存图片本身），保留最近 60 条 |
| 隐私 | 全程在本机完成，**不联网、不上传**，断网可用 |

#### 为什么 WebP 用自带编码器而不是 Canvas

Chrome / Edge / Firefox 的 `toBlob('image/webp')` 背后其实也是 libwebp，但只暴露一个 quality：`method`、色度滤波、分段数这些真正决定体积的参数一概锁死，而且**没有无损模式**。换成自带编码器（libwebp 编译成 WASM，随项目托管，不引外链）之后，同一张图同样质量：

| 场景 | Canvas | WASM 编码器 | 收益 |
|---|---|---|---|
| 照片 1600×1200 @82% | 229.3 KB | **195.1 KB** | −15% |
| 截图 1179×2556 @82% | 9.9 KB | **9.3 KB** | −6% |
| 截图 1179×2556 无损 | 不支持 | **5.7 KB** | 比原图 12.3 KB 还小 54% |

对截图、UI 图、图表这类颜色少的图，**无损输出常常比有损还小**，而且画质一个像素都不差（实测 1205 万个通道逐字节比对，差异 0 个）。所以工具会自动识别这类图并提示改用无损。

顺带修掉一个坑：Canvas 的 `quality` 逼近 1 时输出会突然膨胀（实测 12 KB 的图能编出 341 KB）。现在质量拉满走的是真无损，不再有这个问题。

**关于 iOS / Safari**：WebKit 至今不支持用 Canvas 导出 WebP，而 iOS 上所有浏览器都是 WebKit —— 这也是为什么以前在 iPhone 上只能选 JPEG。WASM 编码器自带 libwebp，不受这个限制，**所以 iPhone 上现在也能转 WebP 了**，且同样支持无损。

#### 编码器的加载与降级

| 事项 | 做法 |
|---|---|
| 体积 | 只托管 encoder（不要 decoder，浏览器自己能解码）。两个版本按运行时 SIMD 支持二选一，**实际单次下载约 121 KB（gzip）** |
| 时机 | **打开图片转换工具时才开始加载**，不进首屏。挑图、调参数的功夫它就下完了 |
| 缓存 | 走 Service Worker 的按需缓存，第二次打开即离线可用 |
| 跑在哪 | 独立 Worker。method=6 编一张 600 万像素的图要 1.8 秒，放主线程就是整段界面冻结 |
| 降级 | 任何环节失败（不支持 module worker / wasm 加载失败 / 编码报错）都会如实说明并回退 Canvas 路径，不静默失败 |

### GITHUB 链接转换

粘一条 GitHub 链接，一次给出所有能用的地址：**加速代理**（前缀型镜像站）与 **CDN 重写**（jsDelivr、GitHack、Statically）。

转换分两段跑：第一段**纯本地**，瞬时出全部结果；第二段按需**联网校验版本**，回来后只重建 CDN 那一组 —— 所以校验期间结果已经可用，不会卡住输入。

#### 两类地址

| 类别 | 规则 | 适用范围 |
|---|---|---|
| **加速代理** | 把原始链接整条拼在镜像域名后面：`https://gh-proxy.com/https://github.com/u/r/raw/main/a.js` | 任何 GitHub 链接 —— 仓库文件、Release 附件、源码包、`git clone` |
| **CDN 重写** | 改写成 CDN 自己的路径格式：`https://rawcdn.githack.com/u/r/main/a.js` | 仅仓库内的文件或目录，但走 CDN 节点，通常更快 |

共 8 个加速代理（gh-proxy.com、ghfast.top、ghproxy.net、mirror.ghproxy.com、github.moeyy.xyz、hub.gitmirror.com、gh.llkk.cc、gh.jiasu.in）与 5 个 CDN（jsDelivr 三个节点、GitHack、Statically）。

**适用性是自动判断的**，不是无脑复制一份：

- Release 附件（`/releases/download/…`）与源码包（`/archive/…`）路径里虽然也带斜杠，但它们不在仓库文件树里，任何 CDN 都取不到 —— 所以只给前缀代理，不给 CDN。
- 目录（`/tree/…`）只有 jsDelivr 与 Statically 支持，GitHack 会被跳过。
- 仓库文件（`blob` / `raw`）代理时会自动换成 `/raw/` 直链 —— blob 页面是 HTML，代理回来的是网页而不是文件本体，下载场景不合适。

#### 版本校验（可选，全站唯一联网的地方）

开启后会调一次 `api.github.com`：

- **短 hash 补全为完整 40 位 commit** —— jsDelivr 对 commit 地址永久缓存，比分支链接（缓存 12 小时）可靠得多；
- **tag 与分支校验存在后保持原样** —— tag 可读且稳定，改成 hash 反而不好维护。

校验只影响 CDN 那一组链接，代理链接始终用你给的原 ref。查不到、超时或命中配额限制都会**退回未校验状态并在界面上写明原因**，链接照常可用，不会因为校验失败就什么都不给。

未登录时 GitHub API 每小时 60 次配额，因此批量超过 20 条时只解析前 20 条并如实标注。

#### 输入与其它能力

| 能力 | 说明 |
|---|---|
| 支持的输入 | `github.com/…/blob/…`、`/raw/…`、`/tree/…`、`raw.githubusercontent.com/…`、`/releases/download/…`、`/archive/…`，每行一个，自动去空行与重复 |
| 结果徽标 | 文件 / 目录 / 仓库，一眼看清每条链接的性质 |
| 复制 | 单条或全部；三种格式可选：纯链接 / `<script src="…">` / `@import url("…")` |
| 实时性 | 边打字边出结果，本地计算无延迟；联网校验分段回填，不会卡输入 |
| 草稿 | 输入框内容实时落盘，关掉页面再打开还在 |
| 历史 | 记录用过的链接（按输出地址去重，最多 30 条），可一键取回 |

**与参考实现（`github2jsdelivr v1.0`）的关系**：转换逻辑、正则、API 语义、`latest` 处理、短 hash 补全规则全部对齐，28 条用例逐条比对输出一致。在此之上补了几处它没有覆盖的情况：

| 输入 | 参考实现 | 本实现 |
|---|---|---|
| `…/blob/main/a.js#L10-L20` | 行号锚点混进文件名 → 链接错误 | 剥离 `#…` 与 `?…` |
| `…/tree/main/src` | `main` 被当成文件名 → 链接错误 | 识别为分支 + 目录 |
| `https://www.github.com/…` | 不匹配 | 支持 `www.` |
| `…/repo.git/blob/…` | 仓库名带 `.git` | 自动去掉 |

**关于可用性**：镜像站都是第三方公益服务，域名随时可能失效。所以工具只负责生成候选地址，**不做可用性探测** —— 探测会被 CORS 拦住，而且不该把你的链接挨个往第三方服务器上发。生成一串之后挑一个能打开的用就行。

**安全提醒**：镜像请求会经过第三方服务器，只用来下载公开资源，**不要带 Token、Cookie，也不要传私密文件**。

### 日期天数计算

两块功能，对应常见日期计算器的用法：

| 块 | 做什么 | 说明 |
|---|---|---|
| **计算日期** | 从某天往前 / 往后推 N 天、周、月、年 | 两个方向同时显示，改一边不用重填另一边；附「回到今天」与 7/30/90/100/365/1000 天快捷 |
| **计算日期间隔** | 两个日期相隔多少天 | 可勾选「包含起始日」（同一天算 1 天）；下方给出折合年月日与周数 |

**三个容易算错的地方，都单独处理了**：

- **月末进位** —— 1 月 31 日往后 1 个月是 **2 月的最后一天**，不是 3 月 3 日。闰年时是 2 月 29 日。
- **天数差用四舍五入而不是向下取整** —— 夏令时切换那天只有 23 小时，`floor` 会少算一天。
- **解析日期后回读校验** —— `new Date(2026, 1, 30)` 会静默进位到 3 月 2 日，必须挡掉，否则用户输入的无效日期会被悄悄改成别的日子。

全部按**本地日期**算，时间一律归一到当天 00:00，时分秒不参与，所以不会出现「差一天」这种时区误差。倒推月份同样处理：`2024-02-29` 往后 1 年是 `2025-02-28`。

日期输入用的是原生 `<input type="date">`，手机上会直接调起系统的日期选择器。

## 四、如何新增一个工具

三步，不需要动其它任何文件：

**1. 在 `js/registry.js` 的 `T.GROUPS` 里确认分组存在**（不存在就加一行），并在 `T.TOOLS` 里补一条：

```js
'my-tool': {
  id: 'my-tool', group: 'calc', name: '我的工具', icon: 'calculator',
  status: 'ready',                       // ready = 已实现；soon = 路线图上
  sub: '一句话副标题',
  desc: '在概览页里展示的说明文字。',
  tags: ['标签一', '标签二']
}
```

**2. 新建 `js/tools/my-tool.js`**：

```js
(function (T) {
  T.register('my-tool', {
    render: function (host, tool) {
      host.innerHTML = '<div class="panel"><div class="panel__bd">…</div></div>';
      // 绑定事件、首次渲染
    },
    onLeave: function () {
      // 清理计时器、Object URL、document 级事件监听
    }
  });
})(window.Toolbox);
```

**3. 把文件加进 `js/loader.js` 的 `ASSETS` 数组**（放在 `js/app.js` 之前），并加进 `sw.js` 的 `SHELL` 预缓存清单。

侧拉栏、概览页、路由会自动出现这一项。需要新图标就往 `index.html` 的图标池里加一行 `<symbol id="i-名字">`，然后写 `T.ic('名字')` —— 不用新建文件、不用改文件名、不用动缓存清单。

### 图标系统（SVG sprite）

44 个界面图标内联在 `index.html` 顶部的 `<svg style="display:none">` 里，每个是一个 `<symbol>`：

```html
<symbol id="i-image" viewBox="0 0 24 24"><rect x="3" y="4.5" width="18" height="15" rx="2.2"/>…</symbol>
```

取用：`T.ic('image')` → `<svg class="ic" aria-hidden="true"><use href="#i-image"/></svg>`

v1.5.0 把原本 45 个独立 `.svg` 文件合并了进来，理由是实打实测出来的：

| | 独立文件（≤ v1.4） | 内联 sprite（v1.5+） |
|---|---|---|
| 首次加载传输量 | **11.7 KB**（逐文件 gzip 之和） | **2.9 KB** |
| 请求数 | 45 个，且每个都要运行时回填进 SW 缓存 | **0** |
| `file://` 可用性 | 需降级为 `<img>`，且不跟随主题换色 | 与 HTTP **完全一致** |
| 加一个图标 | 新建 `.svg` + 命名匹配 + 改进 `sw.js` 缓存清单 | 加一行 `<symbol>` |

**小文件是 gzip 最差的场景**：每个文件 340 字节里约 190 字节是重复的 `<svg>` 外壳与深色媒体查询，压缩字典还没热身就结束了，逐文件 gzip 只能压到 26%（15.5 KB → 11.7 KB）；合并后同样的内容能压到 17%（15.5 KB → 2.9 KB）。

**顺带删掉的复杂度**：`<use href="#...">` 是文档内引用，不受 CORS 约束，所以「按协议在 `mask` 与 `<img>` 之间切换」的整个降级分支没了 —— 连带 v1.0 那个「`mask` 相对路径在样式表所在目录下解析、46 个图标全部 404」的坑也一并根除。

**颜色不写死**：`.ic` 上写 `stroke:currentColor`，继承会穿透 `<use>` 的 shadow tree，图标跟着自身 `color` 走 —— 侧栏选中态、深色模式都自动适配，不需要给 45 个图标各写一份媒体查询。

**favicon 也是内联的**：`<link rel="icon" type="image/svg+xml" href="data:image/svg+xml,%3Csvg…">`。写成 data URI 而不是独立文件，是为了让全站真正做到零 SVG 文件；矢量性质与零请求都没有损失。注意 data URI **必须带 `data:image/svg+xml,` 前缀**，漏掉它浏览器会静默不显示图标（这个坑我在改动时真踩了一次，靠实测才发现）。

### 约定（重要）

- **调用链必须是单向的**。数据层 → 计算层 → 渲染层，渲染函数之间**不允许互相调用**。多个区域需要联动时，收敛到一个 `paint()` / `refreshAll()` 统一入口，由事件处理函数触发它。多个渲染函数互调会形成调用环，直接栈溢出。
- **图标**用 `T.ic('name', '额外class', 尺寸档位)` 生成，输出 `<svg class="ic"><use href="#i-name"/></svg>`。图标定义在 `index.html` 的图标池里，`<symbol>` 内只写 `viewBox` + 路径；描边、填充、线宽、圆角统一由 `.ic` 给（继承会穿透 `<use>` 的 shadow tree），颜色用 `currentColor` 自动跟随主题。风格为 `fill="none" + stroke` 线性，24×24 viewBox。
- **所有用户输入进 innerHTML 前必须过 `T.esc()` / `T.escAttr()`**。
- **新增数据字段必须在 `core.js` 的 `normalizeDB()` 里登记**。`normalize()` 是逐字段重建（不是浅拷贝），漏登记的表现是「存进去了，刷新就没了」。
- **`.pagefoot` 渲染在 `.view` 内部**，横向留白由 `.view` 提供，不要再加左右 padding。

## 五、数据与隐私

- **存储位置**：浏览器 `localStorage`，主键 `lifetoolbox.v1`，快照键 `lifetoolbox.v1.bak`（主数据损坏时自动回退）。
- **不落库**：图片转换记录只保存文件名、体积、尺寸与时间，**图片本身不会被存进浏览器**。
- **不联网**：没有任何后端请求。图片转换的每一步都在本机完成。唯一例外是「GitHub 转 jsDelivr」的版本校验（可在工具内关闭），它只把仓库名发给 `api.github.com`，不发送任何本机数据。
- **草稿**：各工具输入框的内容也会实时落盘（`drafts` 字段），用于「关掉再打开还在」。
- **换设备**：用「数据与设置 → 导出 JSON 备份」迁移；部署到公网后，访客看到的是他自己的空白数据。
- **清理**：清空转换记录 / 清空全部数据都有二次确认。

## 六、启动与缓存策略

### 为什么会有「打开后白屏几秒」

PWA 从主屏启动时，屏幕上的内容分三段来，任一段卡住都是白屏：

| 阶段 | 谁在画 | 曾经的坑 | v1.12 的做法 |
|---|---|---|---|
| 系统启动图 | 操作系统 | iOS 不从 manifest 生成启动图，直接白屏 | 补 `apple-touch-startup-image`（15 种机型 × 浅色/深色） |
| 首帧 HTML/CSS | 浏览器 | 外链样式表阻塞渲染，10 个 CSS 到齐前不画 | 启动遮罩样式内联进 `<head>`，节点放在 `<body>` 第一行 |
| 脚本加载 | 页面 JS | 15 个模块「一个加载完才发下一个」 | 一次性注入全部，并行下载、按序执行 |

第三段曾经最要命：串行注入意味着 15 次网络往返，弱网下每个往返两三百毫秒，
加起来正好是「几秒」。更隐蔽的是 Service Worker —— 它当时是**不设上限的网络优先**，
弱网下 `fetch` 会一直挂着不 reject，缓存里明明有货也要干等。

### 现在的策略

`sw.js` 按「这个请求是不是卡在首帧前面」分成两类：

| 请求 | 策略 | 为什么 |
|---|---|---|
| 导航（HTML） | 网络优先，上限 1500ms | HTML 必须拿到最新的，否则新页面配旧脚本；弱网超时则先用缓存渲染 |
| 脚本（除 loader） | 网络优先，上限 600ms | 新旧脚本混搭会把页面跑挂，宁可多等一个超时 |
| CSS、`loader.js`、`splash/` | **缓存优先**，后台更新 | 它们卡在渲染前面；走缓存最多一次性样式偏差，代价远小于干等 |
| WebP 编码器（`assets/wasm/`、`js/worker/`） | **缓存优先**，按需缓存 | 约 121 KB，只在打开图片转换工具时才需要；第一次用到时下载并缓存，其后离线可用。不进预缓存列表，免得每个访客都背 |
| `version.json` | 完全不拦 | 它是「有没有新版本」的探针，走缓存等于问自己 |

**超时兜底的收益**（服务端对每个请求固定延迟 1 秒，模拟弱网）：

| | 首帧 | 启动完成 |
|---|---|---|
| 改造前 | 3028 ms | 18098 ms |
| 改造后 | **1032 ms** | **1643 ms** |

首帧 1032ms 已经等于导航请求的网络耗时 —— 再快只能让 HTML 也走缓存，
那就牺牲了「换版即生效」，不划算。

### 换版一致性

资源 URL 不带内容指纹（就是 `core.js`、`base.css` 这种裸名字），所以策略的核心是
**不让新 HTML 配上旧脚本**。三道保险：

1. 脚本一律网络优先（有网时必然拿到与 HTML 同时部署的那份）；
2. 预缓存列表随 `CACHE` 名一起换版，新 SW 安装时把全部资源重新拉一遍；
3. `skipWaiting` + `clients.claim`，新 SW 一接管就自动刷新一次页面。

代价是换版瞬间可能出现「新 HTML + 旧 CSS」的短暂不一致 —— 最多是样式偏差，
且下一次打开就是一致的。

### 关于版本号

发版时**三处必须同步改**，缺一处老访客会一直看到旧版：

- `version.json` 的 `ver`
- `js/core.js` 的 `APP_VER`
- `sw.js` 的 `CACHE` 名

### 发布

**发版即上线。** 每次版本号一改，紧接着就同步到线上分享链接，不再逐次确认。

链接固定不变，内容是**覆盖式**替换，对所有已经拿到链接的人立即生效 —— 所以发版前务必先在本机把上一节的验收过一遍，别把半成品推上去。

推送后核对三件事：`version.json` 的版本号、关键文件的 MD5 与本地一致、已删除的旧文件返回 404（确认是全量替换而不是增量残留）。

## 八、设计语言

克制、高级、有生活感，刻意避开「一屏圆角卡片」的模板感：

## 九、已知限制

1. **`file://` 打开时** Service Worker 不注册，因此没有离线缓存；其余功能与图标显示均与 HTTP 完全一致。（v1.5.0 起不再需要图标降级路径。）
2. **WebP 编码能力**取决于浏览器。Chrome / Edge / Firefox 可用；**Safari 与所有 iOS 浏览器不可用**（WebKit 限制），会自动改用 JPEG/PNG 兜底并在界面说明，不会静默失败。
3. 单张图片超过 4000 万像素会先自动等比缩小，避免 Canvas 尺寸超限。
4. 浏览器存储配额约 5 MB，本项目只存文本记录，正常使用远不会触顶；触顶时会有明确提示。
5. 图标池里有若干图标是给后续工具预留的，对应 `registry.js` 中 `status: 'soon'` 的条目。
6. **WebP 编码器依赖 `module worker`**。Safari 15+ / Chrome 80+ / Firefox 114+ 都支持；更老的浏览器会退回浏览器内置编码（此时 iOS 上仍然出不了 WebP，但会如实说明并改用 JPEG）。
7. **编码器是外部文件，不再是纯单文件**。`assets/wasm/` 与 `js/worker/` 共 4 + 1 个文件，通过 `file://` 直接双击打开时 `module worker` 会被拦、编码器不可用 —— 但工具会自动回退，功能不受影响（这一点与 Service Worker 的 `file://` 限制是同类的）。
8. **iOS 启动图只覆盖 15 种主流机型尺寸**。不在列表里的设备（更老的 iPhone、iPad 分屏等）仍会有一小段系统白屏 —— 这是媒体查询匹配不上导致的，不是 bug。要补尺寸就改 `tools/make-splash.py` 里的 `SIZES`，跑一次脚本，再同步 `index.html` 中的 media 声明（两处必须一致）。

## 十、版本

**版本号规则（自 v1.9.0 起执行）**：

- **第三位 `c`** —— 小更新、修 bug、文案与样式微调；
- **第二位 `b`** —— 新增或移除功能、改变交互结构；
- **第一位 `a`** —— 不兼容的重构（本项目尚未发生）。

发版时三处必须同步改，缺一处老访客就会一直看到旧版本：`version.json` 的 `ver`、`js/core.js` 的 `APP_VER`、`sw.js` 的 `CACHE` 名。

### v1.13.3 — 2026-10-15

**修掉 iPhone 主屏启动的白屏**（用户实测机型 iPhone 15 Pro，纯白 1–2 秒）。

- **导航请求改「缓存优先 + 后台静默更新」** —— 这是白屏的根因。原来是「网络优先 + 上限 1500ms」，看着像不等网络，其实还在等：GitHub Pages 的 `index.html` 首字节实测 1.25 秒，没到 1500ms 上限，于是 SW 判定「用网络结果」，缓存里躺着一份现成的 HTML 却不用，用户盯着白屏等满整个网络往返。
- **为什么是纯白**：启动遮罩是内联在 `index.html` 里的，HTML 没到，第一帧就什么都画不出来。所以白屏时长 ≈ HTML 的到达时间，与脚本、样式无关。
- **顺带补一道兜底**：导航请求若与缓存键差一点点（比如落在站点根目录 `…/worktool/` 而不是 `…/worktool/index.html`），只要缓存里有壳页面就先渲染，绝不为了这点差别让用户看白屏。
- **脚本仍维持网络优先**（上限 600ms）：此时遮罩已经画出来了，用户看到的是进度条而不是白屏；新旧脚本混搭的代价则远大于多等 600ms。
- **`sw.js` 注册加 `updateViaCache:'none'`** —— GitHub Pages 给静态文件发 `max-age=600`，不绕过的话新版本可能被浏览器自己的 HTTP 缓存压住最多 10 分钟。
- 排查中顺带核实：iPhone 15 Pro（393×852 @3）的启动图声明齐全、30 张 PNG 尺寸逐张与文件名一致、线上 MIME 全部正确——启动图这条线没有问题，白屏不在那里。

### v1.13.2 — 2026-10-15

- GITHUB 链接转换的两个转换设置默认改为**关闭**：「联网校验版本」（不再默认向 api.github.com 查询）、「latest 省略版本段」。工具与其他工具一样默认全程本地计算，需要校验或省略版本段时在右侧「转换设置」里手动打开。

### v1.13.1 — 2026-10-14

- 图片工具页底部文案原写「转换在浏览器里用 Canvas 完成」，接入 WASM 编码器后已不准确，改为「转换全部在本机浏览器内完成」。功能无变化。

### v1.13.0 — 2026-10-14

**图片格式转换接入 libwebp WASM 编码器**，白拿 15% 体积，还解锁了无损与 iOS。

- **有损用 method=6** —— Canvas 的 `toBlob` 背后就是 libwebp，但只暴露 quality，method 锁死在默认档。实测同一张照片同样质量，method 4 → 6 直接省 15%（229.3 → 195.1 KB）。
- **新增真正的无损模式** —— 质量滑块拉到 100% 即无损。截图、UI 图、图表这类颜色少的图，无损输出比 Canvas 的有损还小（12.3 KB 原图 → 5.7 KB，−54%），画质一个像素都不差（1205 万个通道逐字节比对，差异 0）。滑块上限从 98 提到 100，并在界面标注「100% = 无损」。
- **iOS 也能转 WebP 了** —— WebKit 不支持 Canvas 导出 WebP，以前 iPhone 上只能选 JPEG；WASM 自带编码器绕开了这个限制。
- **自动识别图形类并提示** —— 抽样统计颜色数，颜色少又有损编码时提示可改无损，不替用户做决定。
- **修掉一个 Canvas 的坑** —— `quality` 逼近 1 时输出会突然膨胀（12 KB 的图能编出 341 KB），现在质量拉满走真无损，并给 Canvas 路径压了 0.98 的上限。
- 编码器自托管、不引外链，只托管 encoder（不要 decoder），按运行时 SIMD 支持二选一，**实际单次下载约 121 KB（gzip）**；**打开工具时才加载**，不进首屏，实测首页零 wasm 请求。
- 编码跑在独立 Worker：method=6 编一张 600 万像素的图要 1.8 秒，放主线程就是整段界面冻结。
- 开发中修掉两个自己写的真 bug：Worker 缓存命中时返回了裸 instance 而不是 `{mod, simd}` 包装，导致编码永远静默失败并回退 Canvas；以及 `encode()` 返回的是 `Uint8Array` 而非 `ArrayBuffer`，直接 transfer 会抛「不是可转移类型」。

### v1.12.0 — 2026-10-14

**启动提速**：PWA 冷启动从「几秒白屏」压到 1 秒出首帧。详见「六、启动与缓存策略」。

- **加载链由串行改并行** —— 原来是「一个模块加载完才发下一个」，15 个模块就是 15 次网络往返，弱网下正好是那几秒；现在一次性注入，`async=false` 保证仍按 core → … → app 的顺序执行。
- **Service Worker 每个请求加网络等待上限**（导航 1500ms、脚本 600ms），超时立刻用缓存渲染，网络结果在后台回填。原来不设上限，弱网下 `fetch` 一直挂着不 reject，缓存里明明有货也要干等。

### v1.6.0 — 2026-10-03

起因是一个真实反馈：**iPhone 上从相册选实况照片，工具只显示静态图**。查下来这不是 bug，是 iOS 的系统限制，于是把「说清楚 + 给出可行路径」两件事都做了。

- **确认了根因**：Web 平台没有读取 Live Photo 的接口。原生 App 用 `PHLivePhotoView` / `kUTTypeLivePhoto`，而浏览器 `<input type="file">` 走系统照片选择器，Apple 明确说明这条路径**只回传静态那一帧**，视频轨在交给网页前已被剥离。照片 App 的「存储到文件」同样会移除视频。**任何网页都绕不过去**，此前界面没有解释，容易被当成工具坏了。
- **新增 iOS 专属引导栏**（`iosGuideHTML`）：只在该设备渲染，讲清原因并给出三条可行路径 —— ① iOS 18+「存储为视频」；② macOS「导出未修改的原片」拿 HEIC+MOV；③ 直接给 `.livp`。iPadOS 13 起 UA 伪装成 macOS，靠 `maxTouchPoints > 1` 一并识别。
- **新增「视频首帧补图」**：只有视频轨没有静态图时，用 `<video>` + `<canvas>` 抽首帧生成 JPEG 当静态图。这样走「存储为视频」的 iPhone 用户，依然能拿到「静态图 + 视频」两个文件。派生的图带 `derived` 标记，界面标注「视频首帧」「从视频首帧生成」，且不提供「另存为 JPEG」。
- 抽帧的工程细节：iOS 上必须 `muted` + `playsInline` 才会解码；首帧常停在未解码状态，要 seek 一小段才真正出画；15 秒超时兜底；超过 200MB 的视频跳过抽帧以免吃满内存。
- 引入 `effStill()` 作为静态图的**统一取用口**（原生图优先、派生图兜底），下载、统计、徽标、按钮文案全部走它，避免各处各自判断 `g.still` 造成不一致。
